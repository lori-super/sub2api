# K3 Base64 视频 URL 桥接方案

## 1. 背景与结论

2026-09-02 的生产验证结果：

- 极小 Base64 视频仍能成功，说明上游没有完全移除 Base64 视频能力。
- 约 600KiB Base64 视频首轮约 364 秒后返回 502，重试后总耗时约 380 秒才成功。
- 38.82MiB、45 秒的视频通过 URL 输入约 96 秒成功，上游完整拉取约 40.7MB，识别结果正确。

因此，本次用户可感知问题主要是上游更新后的 Base64 视频处理性能回退。Sub2API 当前只是原样透传，并未主动破坏兼容，但需要增加一层可控的 URL 桥接，避免请求长时间挂起。

最终决策：

1. 对现有 K3 Chat 兼容客户端保持透明兼容，将提供商扩展 `messages[].content[].video_url.url` 里的 Base64 Data URI 流式转存到私有 R2，再把短期签名 URL 发给上游。
2. 管理员可按请求入口、最终账号和映射后模型限制桥接范围；K3 视频最终出口固定为 Chat Completions。
3. 不设置固定业务并发硬上限；容量由实时资源、带宽、存储健康和节点数量决定。
4. 所有首期运行参数进入管理员后台并支持热更新；分层继承、审计和回滚属于目标态。
5. 为高流量客户端提供可选的 R2 直传路径，Base64 桥接长期作为兼容路径保留。

### 1.1 当前开发状态（2026-09-02）

第一阶段代码默认 `off`，部署不会自动启用；启用前必须由管理员完成存储探针与灰度配置。存储基础设施已完成以下准备：

- 已在现有 Cloudflare 账号中新建独立私有桶 `worldcodes-sub2api-media-bridge`，位置为 WNAM、存储类为 Standard；未配置自定义域、`r2.dev` 或 CORS；
- 已为 `media-bridge/` 前缀配置生命周期规则：对象及未完成分片在 24 小时后进入 Cloudflare 的异步清理流程；规则定义固化在 `deploy/r2-media-bridge-lifecycle.json`；
- 已创建仅限该桶的对象读写凭据，并在 OVH 以 `root:root 0600` 暂存于 `/etc/worldcodes/media-bridge-r2.bootstrap.env`。应用部署后必须通过后台真实探针写入加密数据库，随后删除该引导文件。

第一阶段代码状态：

- 已接入最终 Chat Completions 出口和请求级重试缓存；Chat 与 Responses 两个入口可通过各自明确的非官方视频兼容字段输入，Responses 会先适配为 Chat，再桥接最终 Chat 内容中的 `video_url`；这些字段不得表述为 OpenAI 官方视频语义；
- 已实现 MP4 Data URI 严格校验、流式 Base64 解码到私有 R2、短签名 URL 替换和请求结束延迟删除；
- 已将动态内存准入前移到 Chat/Responses 请求体读取之前；已知长度一次预留，未知长度按块渐进预留，准入失败不会继续把大 Body 读入堆内存；
- Chat 入口按两份请求体工作集做动态内存预留，并在模型/策略的全量 Body 改写前先移除大 Data URI，避免高并发时产生多份 Base64 峰值副本；
- Responses 会在完整协议反序列化前直接把原 JSON 中的视频 Data URI 物化并替换成短 URL，避免转换链产生多份大 Base64；
- 已实现单节点在途请求/字节、租户权重、上传带宽、内存保护及 R2 熔断；带宽排队预测超过 `admission_wait_ms` 时立即返回 `429 + Retry-After`，业务并发和带宽配置为 `0` 时不设固定硬上限；
- 已实现后台热配置、入口范围多选、灰度、文件策略，以及独立加密的 R2 凭据保存、二次验证和真实 PUT、鉴权 HEAD、签名 Range GET、删除探针；
- 已做到非 Base64、非目标模型或非目标账号的请求不依赖 R2 可用性。

以下仍属于高流量后续阶段，本文把它们保留为目标而非已交付能力：

- 真正的入口流式 JSON 扫描与边收边传。当前已经先准入并消除 Responses 转换副本，但 Chat/Responses 仍会各保留一份原始 JSON Body；
- Redis 集群租约、跨节点租户额度和跨节点配置 CAS；
- 可选客户端直传、完整监控面板、审计回滚和 `observe` 命中指标；
- 持久化清理队列。当前异常退出后的残留对象由运维侧 R2 生命周期规则兜底；该规则不承诺精确删除时刻，后台暂不展示一个无法执行的“对象硬 TTL”开关。

## 2. 目标与非目标

### 2.1 目标

- 使用 K3 Chat `video_url` 扩展，以及本文列出的 Responses 非官方视频兼容字段的现有客户端无需改请求格式。
- Base64 视频不再直接发送给出现性能回退的 K3 上游。
- Chat 与 Responses 入口共享同一套最终出口能力判断。
- 上游重试和账号 Failover 复用同一个临时对象，不重复上传。
- 网关不生成完整的解码后二进制副本，不把视频写入 `/tmp`。
- 支持多节点扩容和按租户公平共享容量。
- 管理员可以在线调整开关、灰度、容量、文件、存储连接、签名时长和请求后延迟删除参数。

### 2.2 非目标

- 不把 Responses 视频兼容扩展宣称为官方语义，也不把普通 image/file 或未知字段猜测为视频。
- 不对任意字符串或工具参数中的 Base64 做正则替换。
- 不引入第二套用户、余额、计费、调度或账号池。
- 不在同步 Chat 请求中使用 Redis/Kafka 保存大请求体。

## 3. 总体架构

```text
旧客户端
Base64 请求
  │
  ▼
Gateway 鉴权、配置快照、路由元数据解析
  │
  ▼
识别视频兼容字段并选择 Chat Completions 出口
  │
  ▼
协议适配为 Chat `messages[].content[].video_url.url`
  │
  ▼
Media Bridge
  ├─ 流式 Base64 解码
  ├─ 内容与文件头校验
  ├─ 上传 Private R2
  └─ 生成短期签名 URL
  │
  ▼
最终 Chat Completions 请求
  │
  ▼
K3 上游

新客户端或大流量客户
  ├─ 请求预签名上传凭证
  ├─ 直接上传 Private R2
  └─ 携带 media_id 或临时 URL 请求 Gateway
```

Media Bridge 是无状态组件。第一阶段可作为网关内部模块交付，但接口必须与存储、配置和生命周期解耦，以便后续独立部署和横向扩容。

## 4. 协议与能力模型

入口协议、内部适配链和视频出口契约必须分开描述：

- **桥接接收入口**：Media Bridge 只处理 `/v1/chat/completions` 与 `/v1/responses`；现有 `/v1/messages` API 保持原行为，不接入本方案。
- **账号协议边界**：固定为 Anthropic 协议的账号不参与 Media Bridge，也不会被强制改写为 Chat；需要桥接的 K3 账号应配置为 Chat Completions 或 Responses 能力。
- **桥接入口范围**：管理员可多选哪些请求入口有资格触发 Media Bridge；空数组表示不增加入口限制，不是“全部禁用”。
- **视频兼容输入**：Chat 使用 `video_url`；Responses 使用明确的 `input_video` / `video_url`（以及能明确判定为 MP4 的兼容 `input_file`）。这些都是项目兼容扩展，不是 OpenAI 官方视频字段。
- **内部适配链**：检测到符合范围和策略的视频兼容输入后，先选择 Chat Completions 出口，再把 Responses 输入适配成 Chat `video_url`。
- **视频出口契约**：第一阶段只识别最终 Chat Body 中的 K3/OpenAI-compatible 提供商扩展 `messages[].content[].video_url.url`。

管理员配置采用以下最小模型：

| 管理项 | 第一阶段值 | 语义 |
| --- | --- | --- |
| Media Bridge 接收入口 | Chat、Responses | `/v1/messages` 不接入本方案 |
| 桥接入口范围 `scope.ingress_protocols` | 默认全选，可多选 | 只限制桥接资格；空数组表示不限制这两个入口，不代表官方协议定义了视频字段 |
| K3 视频最终出口 | Chat Completions | 固定值；现有后端字段 `scope.upstream_protocols` 固定保存 `openai_chat_completions` |
| 视频字段方言 | Chat `video_url`、Responses 明确视频字段 | 均为兼容扩展，不冒充 OpenAI 官方视频字段 |
| 原生 Responses 出口 | 不用于本桥接 | 命中明确视频兼容字段时先选择并适配到 Chat 出口；普通 image/file 或未知字段不会被猜测成视频 |

桥接是否启用由以下有效配置共同决定：

- 全局、租户和账号开关；
- 请求入口是否命中 `scope.ingress_protocols`；该数组为空时跳过此项限制；
- 请求模型及渠道映射后的模型；
- 最终选择账号的平台和能力；
- 最终发送的上游协议；
- 媒体字段是否位于本方案明确约定的兼容位置。

协议矩阵：

| 请求入口 | 最终上游 | 行为 |
| --- | --- | --- |
| `/v1/chat/completions` | Chat Completions | 对最终 Body 中精确的 K3 Chat `video_url` Data URI 执行桥接；该字段是提供商扩展 |
| `/v1/responses` | 选择并转换为 Chat Completions | 对明确的非官方 `input_video` / `video_url` 及可明确判定的 MP4 兼容输入适配为 Chat `video_url`，再桥接 Base64 |
| `/v1/responses` | 原生 Responses | 未命中明确视频兼容字段时保持既有协议选择；Media Bridge 不猜测普通字段 |
| 任意入口最终形成 Chat Body | `video_url.url` 已是 HTTPS URL | 精确字段原样透传 |

两个入口先使用各自明确、可验证的兼容字段识别视频并选择 Chat 出口；Responses adapter 随后生成统一的 Chat `video_url`，Media Bridge 最后只在该最终 Chat Body 上物化 Base64。请求级缓存保证同一请求的重试只物化一次。不得把未列入契约的官方 image/file 或未知字段重命名成视频。

## 5. 转换流程

1. 完成 API Key 鉴权，按入口和管理员热配置在读取 Body 前进行动态内存准入；未知长度请求按块渐进预留。
2. 读取并校验当前 JSON 请求体，解析路由元数据和受支持的视频兼容字段，结合入口、账号及模型策略判断资格。
3. 对合格视频请求先选择 Chat Completions 出口。
4. Chat 请求保持兼容结构；Responses 先在原 JSON 字节范围内把视频 Data URI 替换成短 URL，再经 adapter 转成统一的 Chat `video_url`。
5. Media Bridge 在物化时预估解码大小并应用当前有效文件策略；最终 Chat 出口保留一次兜底检查。
6. 使用严格 Base64 解码器边读、边校验、边写入对象存储。
7. 固定可信 Content-Type，生成随机对象键和短期签名 GET URL。
8. 仅把最终 Chat `video_url.url` 替换为签名 URL，其余 JSON 字段保持不变。
9. 所有上游重试和 Failover 复用该对象与 URL；签名剩余时间不足时只重新签名。
10. 请求结束后按配置延迟删除；第一阶段清理失败由 R2 生命周期兜底，后续再接持久化清理任务。

当前 Handler 仍会保留一份完整 JSON 请求体，但读取前已经完成动态内存预留，Responses 转换前也会先去掉大 Base64。后续若继续提高单节点极限，可把读取层升级为真正的流式 JSON 扫描与边收边传；无论是否升级，都不得生成完整解码后二进制副本或把大 Body 囤积进 Redis/消息队列。

## 6. 容量与扩展

### 6.1 不设置固定并发硬上限

`max_inflight_requests = 0` 表示不设置请求数硬上限。此时仍由内存、在途字节、上传带宽和 R2 健康策略保护节点，而不是在代码内固定封顶。

自动容量参考：

- 节点可用内存、RSS 和 GC 压力；
- CPU 使用率；
- 网卡入站、出站和重传；
- R2 上传吞吐、P95/P99 延迟和错误率；
- 当前缓冲字节和活跃上传；
- 集群健康节点数。

资源接近保护阈值时先减速读取和收缩新准入；短暂等待后仍无容量才返回 `429 + Retry-After`。不得为了吸收突发而在内存、Redis 或消息队列中囤积大请求体。

### 6.2 租户公平共享

- 不设置固定“每用户并发 1”。
- 使用租户权重、保留份额、持续带宽和突发额度。
- 租户可以借用其他租户的空闲容量。
- 大客户可绑定独立媒体节点池。
- 本地资源保护由每节点执行；集群租户额度通过 Redis 租约或令牌桶协调，租约带 TTL，节点退出后自动回收。

### 6.3 3Gbps VPS 估算

Base64 对原视频产生约 4/3 的客户端入站流量，网关还需向 R2 上传一份原视频。若 3Gbps 为上下行独立带宽，预留约 30% 后，预计原视频有效转存吞吐约为 180～220MiB/s：

| 平均视频大小 | 理论处理量 |
| ---: | ---: |
| 5MiB | 约 36～44 请求/秒 |
| 20MiB | 约 9～11 请求/秒 |
| 64MiB | 约 2.8～3.4 请求/秒 |
| 100MiB | 约 1.8～2.2 请求/秒 |

若 3Gbps 是收发合计，有效吞吐约为 100MiB/s。最终值必须通过 OVH 到 R2 的真实压测确认。

桥接容量与模型容量分别计算。此前 URL 视频请求约 96 秒，因此持续 10 请求/秒需要接近 960 个 K3 在途槽位，账号池可能先于媒体链路成为瓶颈。

## 7. 管理员配置

配置继承顺序：

```text
全局默认 → 用户或套餐覆盖 → 账号或模型覆盖 → 节点覆盖
```

目标态统一语义：

- `null`：继承上一级；
- `0`：自动或不限；
- 修改后热生效，不要求重启；
- 降低配置不终止在途请求，只影响新准入；
- 后台展示最终生效值、版本、修改人和修改时间；
- 支持审计、一键回滚和紧急排空。

第一阶段先提供全局策略、可多选的桥接入口范围、租户容量覆盖、账号/模型范围、固定 Chat 视频出口和 5 秒跨节点刷新；分层继承、审计回滚及跨节点 CAS 在后续阶段实现。

### 7.1 功能与灰度

- `mode`: `off | observe | canary | on | drain`
- 灰度比例和稳定哈希盐；
- Base64 桥接、客户端直传分别开关；
- Chat、Responses 两个桥接入口可多选，空数组表示不限制入口；K3 视频最终出口固定为 Chat Completions，账号和模型范围可调；
- 后台明确标注 Chat `video_url` 和 Responses 明确视频字段为兼容扩展；允许使用，但不声明为 OpenAI 官方视频能力；
- 故障策略，默认拒绝，紧急情况下允许管理员临时恢复透传。

### 7.2 容量与保护

- 自动或手动容量模式；
- 活跃转换目标；
- 准入等待时间和 Retry-After；
- 持续、突发 MiB/s；
- 内存收缩阈值、紧急保护阈值、最低可用内存；
- CPU 和 GC 阈值；
- R2 延迟、错误率、熔断与半开参数；
- R2 熔断最小样本数 `r2_minimum_samples`，首期默认 `20`；
- R2 上传超时 `r2_upload_timeout_seconds`，首期默认 `600` 秒、管理员可在 `1～3600` 秒内调整；
- 自动扩容参数和节点数量，`0` 表示不限。

### 7.3 租户与文件

- 优先级权重、保留份额、突发额度、每日流量；
- 独立节点池；
- 单文件大小、单请求总大小、单请求文件数；
- 允许的媒体类型；
- HTTP 请求体限制；
- 直传建议阈值。

### 7.4 存储与生命周期

- R2 Endpoint、Region、Bucket、前缀和下载方式；
- 上传超时、重试和分片大小；
- 签名 URL 有效期；
- 请求结束后的延迟删除时间 `request_end_delete_delay_seconds`；

R2 生命周期兜底属于运维基础设施，不由应用后台修改；变更时需同步更新并应用 `deploy/r2-media-bridge-lifecycle.json`。

R2 Secret 必须加密保存且永不回显；测试或修改凭据始终要求真人管理员完成二次验证，不受全局可选 step-up 开关影响。安全校验、凭据保护和日志脱敏不可关闭；业务并发与带宽允许配置为 `0` 表示不限，但 URL 签名时长、字段长度等安全边界仍保留合理上限。

## 8. 存储与安全

- 使用专用私有 R2 Bucket，不使用公开裸链。
- 使用 S3-compatible API 上传，签名只授权单个对象。
- 下载必须支持 GET 和 Range。S3 SigV4 的预签名 GET 不能直接复用于 HEAD，因此不把 HEAD 作为 K3 交付契约。
- 2026-09-02 已在 OVH 用实际 R2 签名 URL 验证：Range GET 返回 206，K3 返回 200；同时确认 K3 会保留签名查询参数且不依赖 HEAD。
- 后台 Ready 只证明私有 S3 数据路径和签名下载可用，无法发现另行绑定的公开域；管理员仍必须在 Cloudflare 侧关闭 `r2.dev` 和公开自定义域。生产专用桶已完成该项人工核验。
- 对象键使用至少 128bit 随机数，不在路径暴露用户 ID。
- 首期严格支持 MP4：声明 MIME 与 ISO-BMFF `ftyp` 文件头必须匹配。
- 不在网关调用 ffmpeg 解析不可信视频。
- 不把视频写入 `/tmp`，当前 OVH 的 `/tmp` 为 tmpfs。
- 日志不得记录原始 Base64、完整签名 URL、签名参数、对象内容或存储凭据。

## 9. 生命周期、失败与计费

建议默认值，均可由管理员修改：

- 签名 URL：60 分钟；
- 请求结束后延迟删除：15 分钟；
- R2 生命周期兜底：对象在 1 天后到期并进入 Cloudflare 异步删除流程，不承诺精确删除时刻。

错误语义：

| 场景 | HTTP 状态 |
| --- | ---: |
| Base64 非法 | 400 |
| MIME 或文件头不匹配 | 415 |
| 超过当前管理员策略 | 413 |
| 当前容量不足 | 429，并携带 Retry-After |
| R2 上传、签名或读取服务不可用 | 503 |
| 上游失败 | 沿用现有 Failover 和错误归一化 |

默认 Fail Closed，不自动回退 Base64，避免重新引入数百秒挂起和重复计费风险。上传尚未请求上游时不产生模型费用；桥接字节、PUT/GET 次数、耗时和清理结果单独记录。

## 10. 可观测性

管理员后台分别展示：

1. Media Bridge：活跃流、准入等待、在途缓冲字节、解码和上传吞吐、R2 P50/P95/P99、429/413/503、RSS/GC/CPU、网卡、临时对象数量与容量、租户 Top-N。
2. K3 上游：账号池可用槽位、在途请求、排队时间、首响应和总耗时、Failover 次数、URL 拉取失败率。

告警和自动保护依据应包括内存、带宽、R2 错误率、R2 延迟、桥接失败率、上游 URL 拉取失败率和新增请求延迟。

## 11. 实施顺序

1. 增加本文档和配置模型，默认 `off`。
2. 建立专用私有 R2、最小权限凭据、签名下载和生命周期。
3. 增加 MediaStore 抽象与 Base64 视频桥接核心。
4. 接入最终 Chat Completions 出口和请求级重试缓存。
5. 增加后台配置、有效值预览、热更新、审计与回滚。
6. 增加监控、资源自适应和熔断。
7. 验证 K3 对签名参数、Range 和上游重试的行为。
8. 执行 64、128 以及自动容量模式压测，直到实际带宽或上游容量饱和。
9. 按 `observe → 内部白名单 → 5% → 20% → 50% → 100%` 灰度。
10. 增加可选直传接口和 SDK 支持。

## 12. 验收清单

- 极小、约 600KiB、38.82MiB 及管理员允许范围内的大视频均能完成桥接。
- 多视频、重复视频、非法 Base64、伪造 MIME 和非 MP4 文件头行为符合契约。
- Chat 的 K3 `video_url` 扩展直接使用最终 Chat 出口；Responses 的明确非官方视频兼容字段先经 adapter 转为 Chat，再完成桥接。
- UI 和文档明确把这些输入标为兼容扩展，不伪装成 OpenAI 官方视频语义。
- 502、网络错误和账号 Failover 不重复上传对象。
- 客户端取消、R2 故障和清理失败不会泄漏长期对象。
- 日志中不存在 Base64、签名参数或凭据。
- 管理员修改配置后，新请求立即使用新版本，在途请求不受影响。
- 管理员选择的桥接入口范围会保存并生效；全部不选时按“不限制入口”处理，且不会关闭任何 API。
- 压测期间核心 API 无明显延迟回归，进程内存稳定且不会因大请求触发 OOM。
- Media Bridge 与 K3 上游容量在后台分别可见。
